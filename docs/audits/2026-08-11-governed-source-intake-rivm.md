## Current repository findings

### 1. RIVM is referenced but not packaged

Current repository documentation already places RIVM in the runtime order:

```text
CAG pre-inference
→ RAG if knowledge is required
→ CAG interruption gate
→ renter selection / execution
→ CAG post-inference
→ RIVM when relational
→ validation
→ telemetry + receipts
→ governed memory / feedback
```

`skills/authored-relational-attention/SKILL.md` also inherits RIVM constraints.

However, there is no canonical `skills/forge-rivm/SKILL.md` package on `main` and no public source-authority declaration that explains how private GIP sources may influence public runtime behavior without being published raw.

**Audit state:** `SPECIFIED`, not yet `IMPLEMENTED` in the portable skill surface.

### 2. Source authority is implicit instead of machine-readable

Project Jennifer already distinguishes repository truth, receipts, adaptive memory and public/private lanes in multiple places, but there is no single machine-readable source-authority registry for uploaded source artifacts.

Without one, future renters can over-retrieve a private root, treat a historical design file as current canon, or confuse a public derivative with the sovereign private source.

### 3. Asset problem is partly intake, not absence

The 2026-08-11 companion asset audit correctly identified malformed repository `.webp` payloads and missing legacy paths. The current user-provided upload packet proves that additional valid image binaries exist outside the repository.

This does **not** prove that every asset named in Issue #25 is present in the current packet. It does prove the repository should support proper source intake with checksums, dimensions, status and namespace instead of path-pointer placeholders.

### 4. Forge bootstrap still needs validation hardening

Current `buildForgeBootstrap()` validates the current instruction and boolean readiness flags but the contract should also reject blank target repositories and blank receipt references when receipts are supplied.

Claim downgrades currently return a rejection message that says correction/supersession is required, but there is no explicit correction/supersession input to permit the documented path.

### 5. Memory Receipt Engine needs deep input/immutability hardening

Current receipt code freezes top-level objects but can still retain mutable nested values inside provenance and risk-observation inputs. Numeric fields also need finite-number validation before clamping.

This is a governance issue because a receipt should not change after issuance through a retained nested reference.
