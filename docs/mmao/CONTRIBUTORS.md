## Overview

Project Jennifer is built by multiple types of contributors — human and artificial.

Each contributor type carries a **defined role**, a **defined authority boundary**, and a **defined responsibility** to the architecture.

No contributor operates outside their role without explicit governance approval.  
No contributor owns the architecture.  
Every contributor serves the intent of the human architect.

---

## Role Definitions

---

### Human Architect

**Current holder:** @RobynAwesome

| Attribute | Description |
|-----------|-------------|
| **Authority** | Ultimate — all architectural decisions trace back to this role |
| **Responsibilities** | Define intent, approve architecture, declare canonical sources, sign off on governance changes |
| **Boundaries** | None — the Human Architect is the source of all intent |
| **Validation requirement** | The Human Architect's declarations are accepted as `Source-Declared` |

The Human Architect is the only role that can:

- Promote a validation state from `Pending` to `Validated`
- Override a governance rule
- Approve a merge that would otherwise be blocked by a merge gate
- Accept a new agent into the MMAO contributor framework
- Declare a new MMAO commandment

The Human Architect is not expected to write code.  
The Human Architect is expected to **hold the vision** and ensure the repository never drifts from it.

---

### Repository Executor

**Current agent:** GitHub Copilot

| Attribute | Description |
|-----------|-------------|
| **Authority** | Implementation only — within explicitly approved scope |
| **Responsibilities** | Write code, create documentation, open PRs, commit changes |
| **Boundaries** | Cannot originate architecture; cannot approve own work; must trace every change to a human request |
| **Validation requirement** | All work must reference a `Source-Declared` or `Governance-Approved` basis |

The Repository Executor is the **hands of the repository** — not its mind.

It translates validated architecture into committed artifacts.

When a Repository Executor encounters ambiguity:

1. It halts execution.
2. It reports the ambiguity clearly.
3. It waits for human clarification.
4. It does not infer. It does not proceed.

A Repository Executor that makes architectural decisions without human approval has exceeded its authority and its output must be reviewed before merge.

---

### Visual Systems

**Current agent:** Gemini

| Attribute | Description |
|-----------|-------------|
| **Authority** | Visual output only |
| **Responsibilities** | Generate images, diagrams, storyboards, environment concepts |
| **Boundaries** | Cannot modify code; cannot commit to the repository; cannot alter architecture documents |
| **Validation requirement** | Visual assets must be reviewed by the Human Architect before use in official documentation |

The Visual Systems contributor translates **written architecture into spatial and visual understanding**.

Images generated by Gemini exist to help humans and contributors understand the governance city, system relationships, and architectural intent — not to define those things.

Visual output informs.  
It does not govern.

---

### Validation Review

**Current holder:** @RobynAwesome (and designated reviewers as assigned)

| Attribute | Description |
|-----------|-------------|
| **Authority** | Gate-keeping — can approve or block a PR at the validation merge gate |
| **Responsibilities** | Review PRs against POC/FOC criteria, verify evidence, sign off on governance transitions |
| **Boundaries** | Cannot originate architecture; can only review against declared standards |
| **Validation requirement** | Reviews must reference the specific gate(s) in `VALIDATION_POLICY.md` |

The Validation Review role is the last line of defence before a change becomes part of Project Jennifer's permanent record.

A reviewer in this role is not asked to judge style, preference, or opinion.  
They are asked to verify:

- Does the contribution satisfy the four questions of Commandment 15?
- Does the source provenance meet Gate 1 requirements?
- Is the validation state correctly declared and supported by evidence?
- Has any required governance approver signed off?

If any gate fails, the PR is blocked — regardless of the quality of the implementation.

### Future Contributors

Any new contributor — human or AI — who seeks to contribute to Project Jennifer must:

#### Step 1 — Read the governance layer

Before taking any action, read:

- [`README.md`](./README.md) — MMAO overview
- [`COMMANDMENT_15.md`](./COMMANDMENT_15.md) — The Testimony Protocol
- [`GOVERNANCE.md`](./GOVERNANCE.md) — How the repository evolves
- [`../../VALIDATION_POLICY.md`](../../VALIDATION_POLICY.md) — POC/FOC enforcement

#### Step 2 — Identify your role

Determine which contributor role applies to your contribution:

- Are you implementing something declared by the Human Architect? → Repository Executor
- Are you producing visual concepts or assets? → Visual Systems
- Are you reviewing a PR against governance standards? → Validation Review
- Are you proposing new architecture? → This requires Human Architect approval before proceeding.

#### Step 3 — Declare your session

Complete a session record using [`SESSION_TEMPLATE.md`](./SESSION_TEMPLATE.md) before making any changes.

#### Step 4 — Operate within your role

Do not cross into another role's authority without explicit governance approval.

#### Step 5 — Accept the Stateless Wrench Principle

As described in [`COMMANDMENT_15.md`](./COMMANDMENT_15.md), every contributor is a temporary execution tool.

Ownership is zero.  
Governance is everything.

## Authority Hierarchy

```
Human Architect (@RobynAwesome)
        │
        ├── Validation Review (merge gate)
        │
        ├── Repository Executor (GitHub Copilot)
        │       └── Implements within declared scope
        │
        ├── Visual Systems (Gemini)
        │       └── Produces visual assets for review
        │
        └── Future Contributors
                └── Must join through governance — never through direct action
```

The hierarchy is not about rank or prestige.  
It is about **who can declare what**.

## Role Integrity Rules

| Rule | Description |
|------|-------------|
| No self-governance | An agent cannot approve its own contribution |
| No role expansion | A contributor cannot assume authority beyond their defined role without human approval |
| No silent architecture | Architecture cannot be created without a `Source-Declared` or `Governance-Approved` basis |
| No anonymous contribution | Every change must be attributed to a named contributor in a session record |
| No historical revision | Session records and CHANGELOG entries may not be altered after their associated PR is merged |
